## VERDICT

The approach is right and the execution is the strongest evidence discipline this field has produced. Guild Wars is instanced, so most of MMO server architecture does not apply — no shared world, no scaling problem — and your connection-scoped design, which would be indefensible in a persistent-world emulator, is close to correct here. That structural luck is why R0–R3 fell in 22 hours — and `PLAN.md` §1.8, added after this review, names a second cause that is not luck: the client is the `Cli` half of a two-target source tree, and `Net\Msg\`, `Engine\Map\Path\`, `Engine\Agent\` and `Gw\Const\` carry no Cli/Srv split at all, so the transport and the navmesh you recovered were code both ends compiled rather than a client's view of it (`studies/srvtree/FINDINGS.md`, checked on two builds four months apart). ### 3.4 Introduce one integer simulation clock before R4b timing is calibrated [server-arch · WEAKENED, narrowed]

**Claim, at its durable scope.** This is a design gap, not a bug with a measurable gameplay cost. The server tells the client how much time has passed and keeps no copy, so it cannot answer "what time is it in the simulation?" — the question every skill activation, aftercast, recharge, condition duration and adrenaline decay will ask at R4b. **Evidence.** `authsrv.py:1394-1413`: `prev_tick = time.perf_counter()` … `delta_ms = int((now - prev_tick) * 1000)` … `prev_tick = now`, inside `while not stop.is_set(): time.sleep(TICK_SECONDS)`. `prev_tick` is a local in a closure; nothing accumulates it, and the truncated sub-millisecond remainder is discarded every tick in the same direction. Meanwhile `hit_enemy` (`:867`) uses `time.time()` for `last_hit` vs `ATTACK_INTERVAL`; `revive_due` (`:924`) for `died_at` vs `REVIVE_AFTER`; `pos_seen` at `:1383/:1668/:2039` gates the click-freshness test at `:1906`. `grep -n 'monotonic' toolkit/authsrv/authsrv.py` returns nothing. *The original finding's 23 s/hour drift headline is real and harmless; drop it.*

**Industry comparable.** **SOURCED:** TrinityCore's `WorldRunnable::run()` computes `diff` from `getMSTimeDiff`, passes exactly that integer into `World::Update(uint32 diff)`, and sleeps the *remainder* — `WORLD_SLEEP_CONST - diff + prevSleepTime`, carrying the leftover forward — so the 50 ms loop holds its rate under load. Every spell, aura and cooldown in that codebase is scheduled in milliseconds against that one diff; nothing consults wall clock. AzerothCore inherits the structure in `MapUpdater`. **The rule shipped cores hold: one integer simulation clock, it is the unit of scheduling, and it is the value that goes on the wire.**

**Recommendation.** Two hours, before R4b timing work. Keep a `sim_ms` accumulator on `state`; advance `prev_tick` by exactly `delta_ms / 1000.0` rather than to `now`, so the remainder carries; move `last_hit`, `died_at` and `pos_seen` onto it (or at minimum `time.monotonic()`); sleep the remainder, `time.sleep(max(0, TICK_SECONDS - work))`, so tick rate degrades visibly rather than silently; record `sim_ms` in the Recorder's per-send event so a capture can be re-analysed for drift later.

### 3.5 Give the agent table the shape the wire already imposes — and guard the dict today [server-arch · WEAKENED, split in two]

**The immediate half, do it now.** `spawn_enemy` mutates `state.setdefault("agents", {})[...]` (`authsrv.py:1096`) from the recv loop (called at `:2329`), while `revive_due` iterates `state.get("agents", {}).items()` from the tick thread (`:976`), and the tick's guard at `:1493-1497` is `except OSError` only. **A second concrete defect found while verifying, worth the same commit:** `agents.py:47` comments `PROP_HEALTH_MAX` as "Sets the maximum AND refills," while `authsrv.py:987-990` records the opposite from observation. One of them is wrong and both are in print.

*Honest narrowing:* no in-repo bug yet demonstrates the desync class this is claimed to prevent. ## The one thing

*From the quality partner.*

**Convert the studies from prose into one build-stamped, machine-readable claim ledger that code, tests and future agents all read from — and make "no claim without a key" a house rule, the way "no ArenaNet bytes" already is.**

The confidence vocabulary is a serialization format for cross-session memory, and nothing in the repo can read it. 708 labels across 14 studies, and "two vocabularies" was generous: **eleven of the fourteen documents open with a label table of their own, declaring ten distinct label sets between them.** No two agree, except that `srvtree` — added this week — copies `areatable`'s four tokens and rewrites all four definitions (`areatable`: UPSTREAM = "Repeatedly wrong below"; `srvtree`: UPSTREAM = "Not ground truth"). A further 170 label tokens are loose in 31 `toolkit/*.py` files, where no table is declared at all. The mapping between any two of these is written nowhere. A claim labelled SOURCED in `agentprops` and one labelled UPSTREAM in `character` cannot be ranked against each other by any rule that exists. A "fact" is a bolded token inside a paragraph. 233 distinct virtual addresses appear across `studies/` and 56 more are hardcoded only in `toolkit/` — 289 in the union. 221 of the 233 appear in exactly one document, and exactly **three** (`0x005FC380`, `0x00813040`, `0x00818210`) appear in more than two. (Criterion: eight-digit `0x00XXXXXX` literals in 0x00400001-0x009FFFFF, excluding this report. At `0e78ef6` the same count gave 206 and 44, so the merge added 27 more addresses to the studies and 12 to the code, and did not increase the overlap by one.) **There is no join column, so no cross-study check is constructible even in principle.**

The repo has already recorded the failure, in its most recent commit. `0e78ef6`: `agentprops/FINDINGS.md` §2 read function `0x00818170` correctly and labelled it SOURCED; `skillcast/FINDINGS.md` §6 later published the opposite conclusion about the same address; nothing caught it; §16 burned a full pass re-deriving from scratch what was sitting two directories away. The commit message states the law itself — *"nothing in this repository cross-checks one study against another — the tests are per-study — so a claim refuted by a sibling can stay in print indefinitely."* **It named a second live instance, the repo has since fixed it by hand, and the fix is the stronger version of the argument.** `agentprops/FINDINGS.md:268` read "All four dispatch tables, and none of them is death — SOURCED" while `toolkit/clientscan/genericvalue.py` enumerates seven. Commit `78bbfc5` corrected it — the heading is now "The dispatch tables", a CORRECTED block records that the word *all* was load-bearing because the section closes the death question by enumeration, and a seven-row table replaces the four. Three things about that fix. It took a **dedicated commit** (one file, 50 insertions) whose entire content was the correction. It was reached by a person reading across, not by anything in the repo that can read across again. And **it did not propagate**: `skillcast/FINDINGS.md:1417` still reads, present tense, *"`agentprops` §3b has the same problem in the other direction: it counts 'all four dispatch tables' and there are seven"* — describing a defect that no longer exists, inside the very paragraph whose subject is that a claim refuted by a sibling stays in print. `skillcast/FINDINGS.md` has been edited twice since the fix landed. The repo's own remedy, recorded in the new `agentprops` §2 subsection, is to file each correction *twice* — once in the study that erred and once in the study that was right — which is a manual join, quadratic in studies, and the single best argument on this page for a key column. The failure mode is not that agents make mistakes. It is that **the correction mechanism is also prose, so corrections do not propagate — including out of the correction.**

Second-order: labels are self-assigned by the same agent that makes the claim, in the same commit. The probe protocol enforces temporal separation for *predictions* (`predicts=` printed before any packet goes out); nothing enforces it for *labels*. No sampling pass re-observes a random OBSERVED claim; no adversarial labeller; no second-agent confirmation. The project has 102 OBSERVED claims and **zero measurement of its own label accuracy** — an unaudited primary control in a project whose entire edifice is the vocabulary. The two hand audits that have happened both scored against the label: `skillcast` §16.5 refuted its own §6, and `78bbfc5` found §3b's SOURCED enumeration was four sevenths of one. Two audits, two hits, and no denominator — nobody knows what the other hundred are worth.

Studies keep their prose and cite claim ids. Constants in `toolkit/` cite claim ids at the call site — they already cite study sections informally, so this is a formalization, not a new habit. One test walks the ledger and fails on: two live claims about the same `subject` with contradictory verdicts; any claim whose `build` is not the build of the pinned exe; any constant citing a claim id that has since been REFUTED.

**Why this and not the highest-severity items.**

Against *back up the vault*: that is an errand, not a change — a `robocopy` and a twenty-line filter, one evening, and it does not compete for the same slot. **Do it tonight, before anything else in this report.** Recommending an errand as the one strategic change wastes the slot.

Against *build the capture harness*: four minutes of scripting against tape you **already have** overturned a panel finding and refuted a dossier claim in this engagement. You do not have a capture shortage; you have a reader shortage. Shipping the harness first buys gigabytes of ArenaNet tape into a system with no instrument that turns a byte into a fact, and the only existing path from observation to content is a human typing a dict into `agents.py`. **The ledger is the harness's destination. Build the destination first, and the harness's acceptance criterion becomes writable for the first time.**

Against *the schema build gate*: that gate is one row in the ledger's schema. It falls out free.

The deciding argument is compounding. Every other finding in this report — the router, the tick clock, the property binding, `0x0039`, the C# decision, the fidelity test — is a one-time fix whose value is consumed the day it lands. The ledger is the only intervention whose value **scales with agent throughput** rather than being outrun by it. Today, more agent hours means more prose, more divergence, more `0e78ef6`-class events, and a larger context problem for the next session. With a keyed ledger, more agent hours means more rows a machine can check against each other — and this project's own governing insight is that a check the artifact can refute beats a check we force true.

It is also the only fix that survives the two futures nobody planned for. When ArenaNet ships the next build, a ledger tells you in one command which claims died; prose tells you nothing and looks unchanged. When the service closes, a ledger's NOT FOUND rows filtered to the server-only subjects **is** the sunset shopping list — generated rather than authored.

The house already has the vocabulary, the discipline and the habit. What it does not have is a key column. That is the change.
