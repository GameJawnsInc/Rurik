# The DESKWORK client-confirmation session, 2026-09-23

**What this is.** The one loopback session that confirmed, on our own retail client, what
DESKWORK-D1, D4 and D5 had shipped as `final-confirmation-needs-run`
([studies/deskwork/PLAN.md](PLAN.md) §3; the `PLAN.md` §8.1 "Desk routes" bullets). Every
case was prepared read-only first — questions, predictions and refutations written before
any launch, every flag and coordinate verified in the tree — and run one variable at a
time with its revert flag as the A/B control. 24 launches: 15 driven by the harness
(hands off), 9 by the owner. Every prediction held. Build 38797 (`vault/run/2026-07-29_…`)
and the slice build (`vault/run/slice`), loopback only; nothing touched ArenaNet.

Labels: everything below is **OBSERVED on our own client against our own server** — it
confirms that the client ACCEPTS and DRAWS what we send. Where the thing we send is itself a
RECONSTRUCTION (the hero add, the suppress reply, an interrupt on a body), this session
does not make it retail's; it makes it safe and working on the client.

Run folders are `vault/captures/harness/<stamp>`; each holds `gamesrv.log`, `report.json`
and the frames.

## 3. What the session found

- **The paper doll's armour order is wrong (the owner, OBSERVED, a screenshot).** Retail's
  armour column reads head, chest, arms, legs, feet; ours reads legs, chest, head, feet,
  arms. The server dresses the EQUIPPED bag with the visual array's numbering (body 2,
  boots 3, legs 4, gloves 5, head 6); the pass-3 note already recorded that retail's bag
  order differs (head 4, boots 5, gloves 6), and our numbering puts each piece in another
  piece's row exactly as the owner saw. Being fixed on branch `desk-inv` against the retail
  tapes' own load cells.
- **A drag between two cells of one bag is a different message: c2s `0x0072`
  [item, bag, slot]**, on no retail tape (the 57 opcodes of `toolkit/authsrv/retail_c2s.json`)
  and unanswered by our server, so the client puts the item back. Being armed on `desk-inv`
  as a RECONSTRUCTION after a static read.
- **The restored-cell log label is stale.** The `0x013E` send for a stored cell prints
  `-> equipped 6` while its bytes say bag 2 slot 2 (`…07000000 02 02`): the wire is right,
  the label is not. Fixed with the order.
- **Session hygiene, for the next one:** a sandbox stack started 2026-09-22 17:53 was still
  listening on 6112 / 6601 with pre-merge code (pids 9440, 28020, 32788); the first run's
  `--replace` cleared it. Check the ports before a session, not only for a running client.

## 5. After the fix: the doll order, confirmed (`20260923T185124`)

The `desk-inv` merge (`967983b5`) dresses the equipped bag in retail's order (body 2, legs 3,
head 4, boots 5, gloves 6 -- measured on all 96 live connections). One harness run, no
input but `i`: the paper doll's armour column reads **helm, chest, gloves, legs, boots** top
to bottom -- retail's order, the owner's report closed (frame `w001-step4.png`). The world
model still wears the helm (the `0x006E` visual array is byte-identical, as designed).
**Open, one question for the owner:** the doll's PREVIEW figure is now bare-headed in the
outpost, where the pre-fix preview showed a coif. The likely reading, UNVERIFIED: the
preview now takes its head from the true head slot and applies Guild Wars' headgear-display
rule for a town (the circled toggle beside the helm row), while before the fix it drew the
legs piece's slot there. Retail's preview in a town is what would settle it.

**The owner's answer (2026-09-23, two retail screenshots): it is the headgear DISPLAY MODE.**
The icon beside the headgear row (and beside each costume slot) is a per-slot drop-down --
Always Show (an eye), Hide in Towns and Outposts, Hide in Combat Areas, Always Hide (the
circled bar) -- and on retail it governs BOTH the paper doll's figure and the world model.
Retail's screenshot shows the eye on the headgear and both costume slots; ours shows the
circled bar (Always Hide) on all three, OBSERVED on `20260923T185124`. So our doll now
obeys a mode we never set, and our world model ignores it: two defects -- the default the
client reads (almost certainly an unsent zero) and the world model not following the mode.
Before the order fix the head row drew the legs piece's slot, which hid both. **Landed on
branch `desk-vis` the same day** (studies/cmsg "The display mode", PLAN-LOG): the mode is
one byte the server sends as `0x00EF` — never sent by ours, so the client read a zero — and
the world body follows it only through the server's `0x006E`/`0x006F`; four slots carry
the toggle (the top-left eye is the cape's), not three. The client confirmation of the
predictions written there is what is still owed here.
